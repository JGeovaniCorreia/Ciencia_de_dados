Camada 0 · Conceito

Um protocolo, não uma linguagem

MCP (Model Context Protocol) é um acordo sobre mensagens que padroniza como uma aplicação que hospeda um modelo conversa com capacidades externas. Reaproveita JSON-RPC 2.0 e define apenas quais mensagens valem e o que cada uma carrega. O problema que resolve é combinatório: sem um padrão, cada aplicação precisa de código sob medida para cada fonte de dados, N×M integrações; com ele, cada lado implementa o protocolo uma vez, N+M. O precedente direto é o LSP (Language Server Protocol), que fez o mesmo entre editores e linguagens.

A direção é vertical: um host ligado a várias capacidades. Comunicação entre agentes pares é outro problema, resolvido por outros protocolos, como o A2A.

As três primitivas, por quem decide usar

PrimitivaQuem decideO que éNo ml-context
Toolso modeloFunções com efeito: consultar, gravar, executar.As 5 ferramentas da camada 3.
Resourcesa aplicaçãoDados legíveis por URI: arquivos, registros, páginas.Não usa.
Promptso humanoTemplates de prompt reutilizáveis, expostos como slash commands.Não usa.

Há ainda o sampling, que inverte a direção: o servidor pede uma inferência ao modelo do cliente. Serve a um servidor que precisa de julgamento sem ter modelo próprio.

O que sustenta o desenho é a descoberta em tempo de execução. Ao conectar, o cliente pergunta o que existe e recebe nomes, descrições e JSON Schemas, sem que nenhum lado conheça o outro de antemão. Por isso um servidor escrito hoje funciona num host que ainda não existe. O custo é que a qualidade da integração passa a depender da descrição e do schema.

O modelo não fala MCP

O modelo emite a intenção de chamar uma ferramenta. O cliente traduz para JSON-RPC, aplica a política de permissão, executa e devolve o resultado como texto. É por isso que o Claude Code pode negar uma chamada sem que o servidor saiba que ela foi pedida, e é por isso que a allowlist do settings.local.json (camada 4) funciona.

O protocolo não raciocina, não planeja e não guarda memória. Também não tem transporte próprio: roda sobre stdio, como aqui, ou sobre HTTP com streaming. A memória deste ambiente vem do banco vetorial das camadas seguintes; o MCP só transporta as chamadas até ele.

Camada 1 · Protocolo

Onde termina a especificação e começa o código do projeto

MCP não é Python e não é um arquivo. É uma especificação: JSON-RPC 2.0 sobre um transporte — aqui stdio — com nomes de método fixos (initialize, tools/list, tools/call). Quem implementa esse protocolo é o SDK oficial (pacote mcp 1.27.1). O código do projeto apenas registra funções e as deixa serem chamadas.

O acoplamento com o protocolo tem duas linhas. Os decorators registram a função; o SDK a invoca quando a mensagem correspondente chega pelo stdin: 

@server.list_tools()   # chamado ao receber tools/list  (linha 164)
@server.call_tool()    # chamado ao receber tools/call  (linha 271)

A única outra costura com o transporte é o stdin que o servidor entrega ao SDK, tratado na camada 2.

Camada 2 · Inicialização

A cadeia de arranque e o handshake em 1,3 segundo

O registro está no escopo de usuário, em ~/.claude.json, e não num .mcp.json do projeto. O cliente faz spawn do .bat, que exporta as variáveis de modo offline e limpa as de SSL antes do Python subir. O alcance é global: todos os projetos do ambiente, não apenas este. 

~/.claude.json  →  run_mcp.bat  →  C:\Python314\python.exe  →  mcp_server.py
   registro           HF_HUB_OFFLINE=1            intérprete          stdio_server()
   (user scope)       TRANSFORMERS_OFFLINE=1
                      SSL_CERT_FILE= (limpa)

O cliente conta o tempo do handshake a partir do spawn. O limite padrão é 30 s; aqui está em 90 s, por MCP_TIMEOUT=90000 no ~/.claude/settings.json. O custo caro do arranque é o import sentence_transformers, que puxa o torch e o scipy (~8 s), mais a carga do modelo. Nada disso roda antes do handshake: o import do módulo só carrega mcp e sqlite_vec, e o resto acontece em três peças. 

def get_model():                         # import + carga sob demanda,
    with _model_lock:                      # protegidos por lock
        if _model is None:
            from sentence_transformers import SentenceTransformer
            _model = SentenceTransformer(EMBEDDING_MODEL)
    return _model

def warm_up_model():                     # thread daemon disparada no main():
    get_model()                            # carrega enquanto o servidor já responde

def detach_stdin():                      # o SDK lê uma cópia do stdin;
    mcp_fd = os.dup(0)                     # o fd 0 do processo passa a ser NUL
    os.dup2(os.open(os.devnull, os.O_RDONLY), 0)
    return TextIOWrapper(os.fdopen(mcp_fd, "rb", buffering=0), encoding="utf-8")

Uma ferramenta chamada antes de o warm-up terminar espera pelo lock e recebe o modelo já carregado. Se a carga falhar, por exemplo com o modelo fora do cache, a ferramenta devolve o erro em texto e o servidor continua de pé: list_knowledge, que não usa vetor, segue respondendo. init_db() permanece no import, porque custa milissegundos.

Armadilha do Windows · stdin compartilhado

A primeira versão do carregamento em segundo plano travou para sempre na primeira busca. O transporte stdio deixa uma leitura pendente no stdin entre as mensagens, e no Windows uma leitura síncrona pendente num pipe bloqueia as outras operações sobre o mesmo handle. Ao importar o sentence_transformers, a DLL de scipy.special consulta o stdin durante a inicialização e fica esperando a próxima mensagem do cliente.

Antes isso não acontecia porque os imports pesados rodavam antes de o servidor começar a ler o stdin. Pelo mesmo motivo, carregar o modelo só na primeira ferramenta, sem thread, também travaria. detach_stdin() resolve: o SDK lê uma cópia do handle e o stdin do processo aponta para NUL.

Decisão · arranque em segundo plano · 2026-10-03

O modelo saiu do nível do módulo depois de dois cold starts que abortaram o handshake, em 27/09 e 03/10/2026, cada um deixando uma sessão inteira sem persistência. O MCP_TIMEOUT de 90 s ficou como rede de segurança: é um teto, e só custa tempo quando o servidor está quebrado.

Custo aceito: uma busca feita nos primeiros ~10 s da sessão espera o warm-up terminar. Medido: 9,5 s logo após o handshake, 0,09 s depois de 15 s.

Camada 3 · Caminho do dado

Duas tabelas espelhadas por id

O banco é um SQLite em ~/.ml-context/knowledge.db, fora do repositório, com a extensão sqlite-vec carregada em cada conexão. Os metadados vivem numa tabela relacional; os vetores, numa tabela virtual vec0. O id é o que costura as duas.

Gravação — save_knowledge

Busca — search_knowledge

Decisão registrada · 2026-09-18

knowledge_vec foi reconstruída de L2 para distance_metric=cosine e ganhou a partition key, por migrate_vec_schema.py. Os vetores não precisaram ser recalculados — a métrica é como o vec0 compara no momento da consulta, não uma propriedade do vetor gravado. Antes da migração, a “similaridade” exibida era 1 − distância L2 apresentada como se fosse cosseno.

Decisão registrada · 2026-10-03 · modelo de embeddings

O all-MiniLM-L6-v2, treinado essencialmente em inglês, foi trocado pelo intfloat/multilingual-e5-small, porque o banco é escrito em português. Num benchmark de 20 buscas parafraseadas sobre os 67 registros da época, o MRR subiu de 0,39 para 0,74 e o acerto entre os 3 primeiros, de 40% para 85%. A dimensão continua 384, então a tabela não mudou; os vetores foram recalculados por reembed_knowledge.py.

As similaridades do e5 ficam comprimidas, em geral entre 0,8 e 0,9 no topo. O percentual exibido serve para ordenar resultados, não como limiar de relevância.

Camada 4 · Governança

O que dispara uma chamada

Nenhuma das camadas acima decide quando gravar. Essa regra está em prosa, distribuída em três lugares — é o que converte um banco vetorial em disciplina de projeto.

OndeRegra
CLAUDE.md (raiz) Consultar com search_knowledge ao iniciar tarefa; gravar decisões; registrar aprendizados ao fechar uma fase CRISP-DM.
.claude/agents/*.md 7 dos 9 agentes carregam a regra de roteamento: impacta arquitetura ou metodologia → banco e tabela do CLAUDE.md; aprendizado técnico ou padrão → só o banco.
settings.local.json Allowlist de permissões: search, save, list e delete rodam sem prompt. update_knowledge ficou fora — pede confirmação.
Divisão de responsabilidades

O CLAUDE.md é a vitrine: versionado, legível por qualquer pessoa que abra o repositório, com as decisões que precisam ser públicas. O banco MCP é o arquivo profundo: local, buscável por significado, com o detalhe de experimento que não pertence a um README. Um registro só entra nos dois quando muda a arquitetura ou a metodologia do projeto.

Camada 5 · Suporte

Sonda de saúde e backup automático

Duas rotinas cercam o servidor. O backup opera sem ressalvas: uma Scheduled Task horária copia o banco para ~/iCloudDrive/Backups/ml-context, com 3 tentativas de retry e retenção das 20 versões mais recentes — o que compensa o banco viver fora do git.

O hook SessionStart roda o mcp_check.py no início de cada sessão e faz três checagens independentes, para que uma falha não esconda as outras. A principal repete o que o cliente faz: sobe o servidor pelo mesmo run_mcp.bat, envia initialize e mede a resposta. O hook inteiro leva cerca de 1,8 s.

Limite da sonda

O hook roda num processo próprio. Ele prova que o servidor consegue subir, mas não que a conexão daquela sessão do Claude Code deu certo, informação que o hook não recebe. Com o handshake em ~1,3 s e o limite em 90 s, essa divergência é improvável. Se as ferramentas não aparecerem, o caminho é /mcp → ml-context → Reconnect: rodar o .bat à mão só serve para ver o erro, porque um servidor stdio atende apenas o processo que o iniciou.
